# 阶段 9 P1：座位方案详情页老师可读性收口设计

**背景**

当前 `RuoYi-Vue3-master/src/views/seating/plan/detail.vue` 的评分明细仍主要展示 `detailJson` 的键值拼接结果，人工调整后的冲突提示虽然补了座位位置，但整体表述仍偏技术字段，老师需要自己再翻译一次。

**目标**

本轮只收口一个 P1 子项目：把方案详情页中的评分明细说明、规则解释和冲突提示改成老师可直接理解的业务文案，不改算法、不改后端接口结构、不新增业务流程。

**范围内**

- 评分明细列的老师可读化解释。
- 常见规则明细的短句翻译。
- 人工调整冲突提示的业务化改写。
- 与上述解释逻辑对应的前端纯函数测试。

**范围外**

- 排座算法与评分权重调整。
- 后端返回字段结构变更。
- 详情页大改版或新增复杂组件。
- 真实浏览器联调之外的系统能力扩展。

**方案选择**

采用“前端解释层抽离纯函数 + 页面最小接入”的方案。

原因：

1. 当前后端 `ruleCode`、`ruleName`、`detailJson` 已足够支撑老师可读化翻译，无需扩大到接口改造。
2. 纯函数更适合用 Node 内置测试先覆盖，能把解释逻辑从大页面里拆出来。
3. 页面只改展示层，风险明显低于动算法或接口。

**设计**

1. 新增一个前端纯逻辑模块，负责：
   - 将常见 `ruleCode + detailJson` 翻译成老师可直接阅读的说明句。
   - 将常见硬规则冲突文本翻译成“规则含义 + 当前座位”的业务提示。
2. `detail.vue` 改为调用该模块，不再直接把 `detailJson` 平铺成技术键值串。
3. 评分表“明细”列文案改成“说明”，让页面语义更贴近老师视角。
4. 未命中已知规则时，仍保留稳定降级逻辑，避免出现空白说明。

**验收标准**

- 评分明细不再直接暴露 `required`、`pairs`、`affected` 等原始技术键名。
- 常见规则项能直接读成中文业务句，不需要老师自行翻译。
- 前排、不能同桌、不能相邻三类常见冲突提示能明确指出当前涉及学生和座位。
- 未识别的明细仍能稳定回退显示，不引入空白或脚本报错。
- 本轮不改变接口、数据库和算法结果。
